## 1. 项目简介

TrueBuddy 是一个 AI 驱动的教学辅助平台，面向教师的五个核心场景：

| 能力 | 说明 | 主要落点 |
| --- | --- | --- |
| 文档 / 教案模板生成 | 以既有 Word 模板为基准，由 LLM + 知识库检索复刻出同格式教案 | `tb-module-doctemplate` / `views/doctemplate/` |
| 作业批改 | 按可配置工作流批量批改作业并导出结果 | `tb-module-homework` / `views/homework/`（已接后端 `/homework/upload`、`/homework/grade`） |
| PPT 生成与放映 | 解析 PPTist / pptx 数据，支持预览与全屏放映 | `views/ppt/` |
| 知识库 | 空间 / 文档 / 分片管理，向量化后供检索增强 | `tb-module-knowledgebase` / `views/knowledgebase/` |
| 模拟会议与演讲稿 | 自托管 LiveKit 会议（屏幕共享带声音 + DataChannel 聊天 + 令牌签发）、讲稿逐页生成，讲稿由放映页朗读（声音随共享轨到学生端） | `tb-module-lecture` / `views/meeting/`、`views/ppt/` |

工程由三部分组成：`backend/`（Spring Boot 4 多模块 REST API）、`frontend/`（Vue 3 + Vite 单页应用）、`docx-mcp/`（Python 实现的 docx MCP 工具服务，由后端以 stdio 子进程拉起）。

> 曾经的第四个部分 `digital-human-worker/`（Node ESM 进程，把后端推来的裸 PCM 发布成 LiveKit 音频轨）已于 2026-10-10 整体删除：讲稿的声音改为后端以 SSE 流回放映页、由本页播放并随屏幕共享到学生端（[16](./16-PPT演讲与模拟会议方案.md) §5.7）；原方案留在 [17](./17-AI数字人语音链路方案.md)（已标废弃）。

## 4. 强制约定摘要

| # | 约定 | 详见 |
| --- | --- | --- |
| 1 | 除 SSE（`POST /chat` 返回 `SseEmitter`）与联调端点（`GET /workflow/text` 返回 `void`）外，后端接口一律返回 `CommonResult<T>`，`code = 0` 表示成功 | [05](./05-API规范.md) |
| 2 | 敏感信息一律环境变量注入，`application.yml` 只写 `${VAR}` 占位符 | [08](./08-通用约束.md) |
| 3 | 前端统一 `<script setup>` + 纯 JavaScript（无 TypeScript） | [02](./02-编码规范.md) |
| 4 | 组件样式默认 `<style scoped>`，全局样式仅限入口声明 | [09](./09-样式规范.md) |
| 5 | 禁止使用 `==` / `!=`，统一使用 `===` / `!==` | [02](./02-编码规范.md) |
| 6 | 禁止 `DO` 暴露到接口层，出入参一律使用 VO / DTO | [05](./05-API规范.md) |
| 7 | 前端导入统一使用 `@/` 别名，禁止跨层级相对路径 | [02](./02-编码规范.md) |
| 8 | 提交前前端须通过 `npm run lint` **与 `npm test`**、worker 须通过 `npm test`；后端须通过 `./mvnw clean install` | [08](./08-通用约束.md)、[11](./11-测试规范.md) |
| 9 | 现状与规划必须分开标注，未实现的能力不得写成现状 | [10](./10-文档规范.md) |
| 10 | 代码与规范不一致时，按「现状 / 规范要求 / 待整改」如实记录 | [10](./10-文档规范.md) |
| 11 | 「在线成员」的唯一真相源是 LiveKit 房间事件，不得由数据库台账计算 | [adr/0002](./adr/0002-在线状态唯一真相源为房间事件.md) |

## 5. 与子项目规约的关系

本目录的 18 个专题文件（01～18）是「规范源」，保持要点化、可执行；`adr/` 与 `specs/` 分别承载不可逆决策与单次变更规格，根目录 [../CONTEXT.md](../CONTEXT.md) 承载领域术语；两份子规约承载更细的实现说明与模块内部约定，二者为「总—分」关系：

- 前端细节：[../frontend/AGENT - 前端技术规约.md](../frontend/AGENT%20-%20前端技术规约.md)
- 后端细节：[../backend/AGENT - 后端技术规约.md](../backend/AGENT%20-%20后端技术规约.md)

> 当本目录与两份子规约描述冲突时，以**实际代码**为准，并按 [10-文档规范.md](./10-文档规范.md) 的流程同步修订文档。

## 6. 生效与维护

- 规范随代码演进：修改规范需在同一变更中说明原因，并同步受影响的文件。
- 旧版「总体技术规约」（`docs/AGENTS.md`）已删除，其内容由本文件与 01~18 号文件取代。
- 任何标注「规划 / 待开发」的能力都代表**尚未落地**，不得据此编写依赖代码；反之，已落地的能力也不得继续留在「规划」标签下（16、17 号已按此口径更新）。
- 根目录 `api.md`（2026-09-26）与 `docx-mcp/`、`.repro/`、`testfile/` 同为历史产物，不作为规范来源；接口清单以 [05-API规范.md](./05-API规范.md) 为准。
