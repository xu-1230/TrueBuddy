### 2.4 分层职责

| 层 | 职责 | 位置 | 约束 |
| --- | --- | --- | --- |
| Controller | 接收请求、参数校验、返回 `CommonResult<T>` | `module/{m}/controller/` | 不写业务逻辑、不直接调 Mapper |
| Service | 业务逻辑、事务边界（接口 + 实现分离） | `module/{m}/service/`、`service/Impl/` | 对外暴露接口 |
| Mapper | 数据访问（`@Mapper` 接口 + `@Select` / `@Insert` / `@Update` 注解 SQL） | `module/{m}/mapper/` | 无 XML、不用 `BaseMapperX`；复杂查询允许动态 SQL（`<script>`） |
| DO | 数据库实体（普通 POJO + Lombok） | `module/{m}/model/` | 不继承 `BaseDO`；审计列（`create_time` / `deleted`）在 SQL 里显式写；不得出现在接口入参/返回值 |
| VO / DTO | 接口出入参 | `module/{m}/model/vo/` | 命名 `XxxReqVO` / `XxxRespVO` |
| Enums | 模块错误码 | `module/{m}/enums/` | 继承 `ErrorCode` 形式 |
| Config | 模块级配置与 `@ConfigurationProperties` | `module/{m}/config/` | 敏感项走环境变量 |

**依赖方向**：`Controller → Service → Mapper → DO`，严格单向。

> 模块特例（现有实现，非通用约定）：
> - `knowledgebase` 额外有 `service/parse/`（`DocumentParseGateway` + `ParseGatewayConfiguration` + `ParseTaskStatus` + `parse/docmind/DocMindParseGateway`）与 `service/chunk/`（`DocumentChunkService` + `AiDocumentChunkService`），分别承载文档解析与 AI 语义分片。
> - `doctemplate` 额外有 `prompt/AiPromptConstants`、`service/DocxMcpGateway`（MCP 网关接口 + `Impl`）。
> - `test` 额外有 `mybatis/handler/`（JSON TypeHandler）。
> - `lecture` 额外有 `livekit/`（令牌与房间）、`digital/`（TTS 与 worker 客户端）、`util/`（局域网地址等），并把讲稿能力放在 `ppt/` 子命名空间下（自成一套 controller/service/model）。
> - `workflow`（`org.example.textflow`）**不遵循 Controller → Service → Mapper 链**：持久化走 `repository/` + `JdbcTemplate`，画布 schema 在 `entity/`，DO 在 `model/`，节点执行在 `node/`，SSE 推送在 `sse/ChatSsePublisher`。

### 2.6 知识库数据模型与处理链路

**四张表**：

| 表 | 职责 | 删除策略 |
| --- | --- | --- |
| `kb_space` | 知识库空间 | 软删（`deleted BOOLEAN`） |
| `kb_document` | 文档元数据与处理状态 | 软删（`deleted_at`，`NULL` = 未删除） |
| `kb_document_parse_block` | 解析产物：版面块（块级，含页码 / 页内序号 / 引擎块 ID） | 物理删 |
| `kb_document_chunk` | AI 语义分片（向量化的最小单位，**不携带类型与标题**） | 物理删 |

**处理链路**（`KbDocumentServiceImpl`）：

```
上传(MinIO + infra_file) → 提交 docmind 解析 → 轮询 parse-status
  →[5] 解析产物落库（块级）
  →[6] AI 语义分片（DocumentChunkService）
  → 分片落库 →[4] 待确认 → 用户校对 →[7] 向量化 →[2] 已完成
任一步失败 →[3] 失败
```

**`kb_document.status` 取值**：

| 值 | 含义 | 值 | 含义 |
| --- | --- | --- | --- |
| 0 | 待处理 | 4 | 分片待确认 |
| 1 | 解析中 | 5 | 解析完成待分片 |
| 2 | 已完成（已向量化） | 6 | AI 分片中 |
| 3 | 失败 | 7 | 向量化中 |

> 版面类型属于 `kb_document_parse_block.block_type`（取值开放，不做枚举约束）；分片层不再冗余类型信息。
> AI 分片只让模型输出「块区间」，正文由后端按区间拼接，模型无法改写原文；模型不可用时回退为「一块一分片」。

> **自定义工作流模块（`tb-module-workflow`）**：工作流定义落库到 `workflow` 表
> （脚本 `sql/workflow.sql`，画布 JSON 整存、`deleted` 软删、**不做版本管理**），
> 接口为 `POST /workflow/save`、`GET /workflow/detail`、`GET /workflow/list`（`/workflow/**` 免登录，另有联调用的 `GET /workflow/text`，返回 `void`）；
> 执行走 **SSE**：`POST /chat`（`text/event-stream`，**只接受已落库的 `workflow_id`，画布不内联提交**）推送
> `conversation.chat.in_progress` → `conversation.message.completed`\* → 终态帧
> （`conversation.chat.completed` / `.failed` / `.requires_action`），每轮都以 `done` 收尾（**判断终态看帧，不看流是否结束**）；
> 人工确认节点中断时连接保持打开，前端再调一次 `POST /chat`（同 `conversation_id` + 卡片勾选值）续跑，
> 首轮与续跑是同一个端点；会话与执行实例落 `workflow_conversation` / `workflow_run`（记 `creator`、按用户隔离），
> **但中断点（`executeId` → `InterruptionMetadata`）与图 checkpoint 仍在内存 Map 里，进程重启即失效**；
> `/chat/**` 故意**不在** `tb.security.permit-all-urls` 白名单内（要求登录），这也是它不挂在 `/workflow` 前缀下的原因。

### 3.3 业务模块目录约定

每个业务模块在 `views/{模块}/` 内**自治**，私有资源就近放置：

| 目录 | 含义 | 现有示例 |
| --- | --- | --- |
| `components/` | 模块内私有组件 | 除 `guides/`、`index/` 外每个模块都有；`meeting/components/` 6 个、`homework/components/` 5 个 |
| `utils/` | 模块内工具函数（**优先在这里写纯函数，配套 `frontend/tests/` 用例**） | `homework/utils/{format,zip}.js`、`meeting/utils/{attendees,chat,meeting-connection}.js`、`system/utils/feed.js`、`workflow2/utils/`（11 个）、`ppt/utils/{slide-text,speech-player}.js` |
| `constants.js` | 模块级常量 / 配置对象（单文件，不放 `configs/` 时用它） | `system/constants.js`、`knowledgebase/constants.js` |
| `stores/` | 模块独享 Pinia store | `ppt/stores/{slides,screen}.js`、`meeting/stores/meeting.js` |
| `hooks/` | 模块内组合式函数（全局的放 `src/composables/`） | `meeting/hooks/useLiveKitRoom.js`、`ppt/hooks/` |
| `node/` | 画布类模块的节点卡片组件 | `workflow2/node/`（5 个） |
| `configs/` `styles/` `mock/` | 画布/放映类模块的常量、私有样式与演示数据 | `ppt/configs/`、`ppt/styles/{animation,prosemirror}.css`、`ppt/mock/` |

> `views/workflow2/` 是**正式的工作流画布**（不再是示例态）：`utils/` 下的执行状态归约、校验与节点工厂都是纯函数并有对应测试；
> 跨组件共享用 `provide/inject`（`RUN_STATE_KEY` / `RUN_ACTION_KEY` / `ITERATION_DROP_TARGET_KEY`），**不是 Pinia**。
> 旧的 `views/workflow/` 与 `views/homework/HomeworkWorkflowView.vue`、`views/homework/mock/`、`homework/utils/workflows.js` 均已删除。

## 4. 讲稿播报的声音链路（取代原 `digital-human-worker/`）

原第 4 节记录的是一个独立的 Node 进程（`digital-human-worker/`，用 `@livekit/rtc-node` 把后端推来的裸 PCM 发布成房间音频轨）。**该目录已于 2026-10-10 整体删除**，链路改为：

```text
放映页(/index/ppt) --POST /ppt/speech/speak--> tb-module-lecture（CosyVoice 流式合成）
      ↑  SSE：status / chunk(base64 的 48kHz 单声道 16bit PCM) / error
      └─ 本页 WebAudio 播放（views/ppt/utils/speech-player.js）+ 逐帧响度驱动口型
         └─ 被屏幕共享（audio: true）──> 学生端 <audio>（screen_share_audio 轨）
```

为什么删：声音的终点本来就是**被共享的那一页**；中继一圈多一个进程、多一份要同步的配置、多一条会挂的链路，而「口型要等远端轨」「取消要额外做接口」这两个代价一并消失。选型经过、代价与验收步骤见 [16](./16-PPT演讲与模拟会议方案.md) §5.7；被推翻的原方案整篇留在 [17](./17-AI数字人语音链路方案.md)（已标废弃，只作历史）。
