## 2. 后端测试规范

### 2.1 目录与命名

```
backend/tb-module-{模块}/
└── src/test/java/org/example/backend/module/{模块}/
    ├── controller/XxxControllerTest.java        # 接口层（@SpringBootTest + MockMvc）
    ├── service/XxxServiceImplTest.java          # 业务逻辑（可 Mock 依赖）
    └── mapper/XxxMapperTest.java                # 数据访问（需真实库，慎用）
```

| 类型 | 命名 | 说明 |
| --- | --- | --- |
| 单元测试 | `XxxTest` | 只测单一类，外部依赖用 Mock |
| 集成测试 | `XxxIntegrationTest` | 启动 Spring 上下文 / 访问数据库 |
| 测试方法 | `方法名_场景_期望结果` | 例：`createSpace_名称重复_抛ServiceException` |

### 2.2 约定

- 测试类与被测类**包路径一致**（`src/test/java` 镜像 `src/main/java`）。
- 使用 JUnit 5（`org.junit.jupiter`）+ `spring-boot-starter-test`（含 AssertJ、Mockito）。
- 断言使用 AssertJ（`assertThat`），不使用 `System.out` 验证结果。
- 涉及数据库的测试必须使用独立测试库或事务回滚（`@Transactional`），**禁止**污染 `tb` 生产库。
- 外部依赖（LLM、Embedding、MinIO、MCP docx-mcp）在测试中一律 Mock 或打桩，不得依赖真实网络与密钥。
- 测试代码同样适用 [02-编码规范.md](./02-编码规范.md)；测试中的固定数据不得包含真实凭据。

### 2.3 命令

```bash
cd backend
./mvnw test                                  # 全模块测试
./mvnw -pl tb-module-knowledgebase test      # 单模块测试
```

### 2.4 建议优先覆盖的模块

| 优先级 | 目标 | 理由 |
| --- | --- | --- |
| 高 | `tb-framework/tb-common`（`CommonResult`、`ServiceExceptionUtil`） | 全项目公共契约，回归成本最高 |
| 高 | `tb-module-knowledgebase`（分片、向量化编排） | 纯逻辑密集，易出错且无需外部依赖（可 Mock） |
| 中 | `tb-module-doctemplate`（规则选择、自检修复编排） | 逻辑复杂，可用 Mock 的 `DocxMcpGateway` 覆盖 |
| 中 | `tb-framework/tb-spring-boot-starter-security`（Token 提取） | 安全相关，需回归保障 |
| 低 | `tb-module-infra`（MinIO 上传） | 依赖外部服务，Mock 成本高于收益 |

## 3. 前端测试规范

### 3.1 现状

- 已有 `frontend/tests/` 下的 `node:test` 用例与 `npm test` 脚本（零新增依赖）：
  `iteration.layout.test.js`（迭代卡片布局口径与折叠往返）、`run-state.iterations.test.js`（迭代进度归约）、`variable-sources.test.js`（抽屉变量候选的迭代体边界）。
- 覆盖范围仅限 workflow2 画布的**纯函数层**；组件渲染、`api/`、`utils/`（auth / 拦截器）仍无覆盖。
- 无 `vitest.config.js` / `jest.config.js` / `cypress/` / `playwright.config.*` 等配置；端到端验收目前依赖人工操作配合浏览器工具。
- `.gitignore` 中的 Vitest / Cypress 忽略项属脚手架残留，不代表已引入。

### 3.2 引入规划

> **规划 / 待开发**：纯函数层的单元测试已用 `node:test` 起步，后续按「组件测试 → 端到端测试」两阶段推进。

| 阶段 | 技术 | 落地位置 |
| --- | --- | --- |
| 单元 / 组件测试 | Vitest + @vue/test-utils + happy-dom | `frontend/src/**/__tests__/` 或同级 `*.spec.js` |
| 端到端测试 | Playwright / Cypress | `frontend/e2e/` |

### 3.3 约定（引入后生效）

| 项 | 约定 |
| --- | --- |
| 测试文件命名 | `*.spec.js`（与被测文件同目录）或放在同级 `__tests__/` |
| 脚本 | `npm run test`（`vitest run`）、`npm run test:watch`（`vitest`） |
| 组件测试 | 优先测行为（props 变更、emit 触发），不断言内部实现细节 |
| 网络 | 使用 `vi.mock` 打桩 `@/api/*`，禁止真实请求后端 |
| 覆盖率 | 优先覆盖 `src/api/`（拦截器与解包逻辑）、`src/utils/`、纯函数工具 |

### 3.4 建议优先覆盖的目标

| 优先级 | 目标 | 理由 |
| --- | --- | --- |
| 高 | `src/api/index.js` 拦截器 | 全站数据流出口，解包 / 错误码逻辑必须稳定 |
| 高 | `src/utils/auth.js` | Token 读写契约 |
| 中 | `views/homework/utils/{format,zip,export}.js` | 纯函数，测试成本低 |
| 中 | `views/ppt/utils/element.js`、`configs/*` | 纯逻辑（ID、颜色、几何计算） |
| 低 | 复杂渲染组件（`viewer/ppt` 元素渲染） | 依赖画布与样式，性价比偏低 |
