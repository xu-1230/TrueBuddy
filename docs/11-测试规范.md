## 1. 总体现状

| 端 | 测试代码 | 测试框架 | 现有质量门禁 |
| --- | --- | --- | --- |
| 后端 | **已存在**：2 个模块 8 个测试类、**59 个 `@Test`**（`tb-module-lecture` 6 类 / 47 例，`tb-module-workflow` 2 类 / 12 例） | JUnit 5 + `spring-boot-starter-test`（Mockito、AssertJ）。**全部是单元测试，零 `@SpringBootTest` / MockMvc** | `./mvnw clean install` 编译 + `./mvnw test` + 人工联调 |
| 前端 | **已存在**：`frontend/tests/*.test.js` **16 个文件 / 178 条用例**，另有 `tests/support/alias-hooks.mjs` | Node 内置 `node:test` + `node:assert/strict`（`npm test` = `node --test "tests/*.test.js"`，零新增依赖） | `npm run lint`（oxlint + ESLint）、`npm test`、`npm run build` |

> **命名陷阱**：`tb-module-test`、`tb-module-test2` 是**业务验证模块**（连通性 / 文档解析验证接口），不是测试代码；它们的源码在 `src/main/java`，不进入 `./mvnw test` 的测试集。
> 结论：三端都已有自动化测试，**「项目没有任何测试」的旧结论已失效**；但组件渲染、`src/api/` 拦截器、端到端流程仍无覆盖，后端也缺少接口层与数据库层测试。

## 2. 后端测试规范

### 2.1 目录与命名

```
backend/tb-module-{模块}/
└── src/test/java/{包根}/{与被测类同路径}/
    ├── service/XxxServiceImplTest.java          # 业务逻辑（Mockito 打桩依赖）——现有主力形态
    ├── util/XxxUtilsTest.java                   # 纯函数工具
    └── controller/XxxControllerTest.java        # 接口层（@SpringBootTest + MockMvc）——**当前一例都没有**
```

> 包根随模块而变：`tb-module-lecture` 的测试镜像 `org.example.backend.module.lecture.**`，`tb-module-workflow` 的测试镜像它自己的包根 `org.example.textflow.**`（现存 2 个类都在 `org/example/textflow/node/`）。**不要**为了「统一」把 workflow 的测试挪进 `org.example.backend` 包下。

| 类型 | 命名 | 说明 |
| --- | --- | --- |
| 单元测试 | `XxxTest` | 只测单一类，外部依赖用 Mock |
| 集成测试 | `XxxIntegrationTest` | 启动 Spring 上下文 / 访问数据库（**尚未使用**） |
| 探针 / 冒烟 | `XxxProbeTest` | 允许真连外部服务，但必须用 `Assumptions` 在无密钥时跳过（现有 `CosyVoiceProbeTest`） |
| 测试方法 | `方法名_场景_期望结果` | 例：`createSpace_名称重复_抛ServiceException` |

### 2.2 约定

- 测试类与被测类**包路径一致**（`src/test/java` 镜像 `src/main/java`）。
- 使用 JUnit 5（`org.junit.jupiter`）+ `spring-boot-starter-test`（含 AssertJ、Mockito）。
- **现状**：断言混用 AssertJ（`assertThat`）与 JUnit（`assertEquals`），新写用例统一 AssertJ；`LiveKitTokenServiceTest`、`CosyVoiceProbeTest` 各有 1 处用 `System.out` 打印结果，属待整改。
- **现状**：Mockito 用法集中在 2 个 `@ExtendWith(MockitoExtension.class)` + 12 个 `@Mock`；没有 `@SpringBootTest`、没有 `@Transactional` 回滚，也没有真实数据库测试。
- 涉及数据库的测试必须使用独立测试库或事务回滚（`@Transactional`），**禁止**污染 `tb` 生产库。
- 外部依赖（LLM、Embedding、MinIO、MCP docx-mcp、LiveKit、DashScope）在测试中一律 Mock 或打桩，不得依赖真实网络与密钥；确需真连的只能做成 `ProbeTest` 并用 `Assumptions` 跳过。
- 测试代码同样适用 [02-编码规范.md](./02-编码规范.md)；测试中的固定数据不得包含真实凭据。
- 单模块跑测试要带上依赖模块，否则 `-pl` 会因找不到 `tb-common` 等而失败：`./mvnw -pl tb-module-lecture -am test`。

### 2.3 命令

```bash
cd backend
./mvnw test                                      # 全模块测试（当前跑 lecture + workflow 的 8 个类）
./mvnw -pl tb-module-lecture -am test            # 单模块测试（-am 顺带构建它依赖的 tb-common 等）
./mvnw -pl tb-module-workflow -am test
```

### 2.4 建议优先覆盖的模块

| 优先级 | 目标 | 理由 |
| --- | --- | --- |
| 高 | `tb-framework/tb-common`（`CommonResult`、`ServiceExceptionUtil`） | 全项目公共契约，回归成本最高 |
| 高 | `tb-module-knowledgebase`（分片、向量化编排） | 纯逻辑密集，易出错且无需外部依赖（可 Mock） |
| 中 | `tb-module-doctemplate`（规则选择、自检修复编排） | 逻辑复杂，可用 Mock 的 `DocxMcpGateway` 覆盖 |
| 中 | `tb-framework/tb-spring-boot-starter-security`（Token 提取） | 安全相关，需回归保障 |
| 低 | `tb-module-infra`（MinIO 上传） | 依赖外部服务，Mock 成本高于收益 |

## 3. 前端测试规范

### 3.1 现状

- `frontend/tests/*.test.js` 共 **16 个文件 / 约 174 条用例**，脚本 `npm test` = `node --test "tests/*.test.js"`，**零新增依赖**（清单见 §1.1）。
- 覆盖重心已从「workflow2 画布纯函数」扩展到 **meeting 模块的纯函数层**（`utils/attendees.js`）、**ppt 播报播放器**（`utils/speech-player.js`）与 **system 首页聚合**（`utils/feed.js`），并有 1 个针对构建产物的守卫用例（`build-artifact.test.js`）。
- **仍无覆盖**：组件渲染（真实挂载 SFC）、`src/api/` 拦截器与解包、`src/utils/auth.js`。
- 在没有 jsdom / @vue/test-utils 的前提下，现有用例用三种手法绕过「不能挂载组件」的限制，新增测试时照此选择：
  | 手法 | 做法 | 现有用例 |
  | --- | --- | --- |
  | 真实函数 + 替身环境 | `readFileSync` 读 `.vue` 源码，按大括号配对抽出函数体，在替身上下文里求值执行 | `run-chain.test.js`（`handleRun` / `showRunValidationErrors`），必要时配合 `vue/server-renderer` 渲染弹窗内容 |
  | 源码契约断言 | 直接对 `.vue` / `.js` 源码做正则断言（防止把某个约束改掉却没人发现） | `variable-sources.test.js` |
  | 别名解析 | `register('tests/support/alias-hooks.mjs')` 注册 `node:module` hook 解析 `@/`，然后**动态 import** 目标模块 | 需要 `@/` 别名或省略扩展名的用例 |
- 无 `vitest.config.js` / `jest.config.js` / `cypress/` / `playwright.config.*`；端到端验收目前依赖人工操作配合浏览器工具。
- `.gitignore` 中的 Vitest / Cypress 忽略项属脚手架残留，不代表已引入。

### 3.2 引入规划

> **规划 / 待开发**：`node:test` 的纯函数用例已是现行手段并可继续增加；下表两阶段仍未落地，引入前不得假设 `*.spec.js` / `__tests__/` 存在。

| 阶段 | 技术 | 落地位置 |
| --- | --- | --- |
| 组件测试 | Vitest + @vue/test-utils + happy-dom | `frontend/src/**/__tests__/` 或同级 `*.spec.js` |
| 端到端测试 | Playwright / Cypress | `frontend/e2e/` |

### 3.3 约定

| 项 | 约定 |
| --- | --- |
| 测试文件命名 | **现行**：`frontend/tests/{行为}.test.js`（集中目录，不散落到 `src/`），限定名用 `.` 分段（`run-state.iterations.test.js`），复现历史缺陷加 `repro-` 前缀；引入 Vitest 后组件测试才允许 `*.spec.js` 同目录或 `__tests__/` |
| 脚本 | **现行** `npm test`（`node --test`）；引入 Vitest 后改为 `npm run test`（`vitest run`）+ `test:watch`，并同步 [02](./02-编码规范.md) §4 与 [08](./08-通用约束.md) §5.1 的门禁表 |
| 断言 | `node:assert/strict`（`equal` 即 `strictEqual`），不引第三方断言库 |
| 组件测试 | 优先测行为（props 变更、emit 触发），不断言内部实现细节 |
| 网络 | 不起真实后端请求：`@/api/*` 一律打桩或用替身环境注入 |
| 覆盖率 | 优先覆盖 `src/api/`（拦截器与解包逻辑）、`src/utils/`、模块 `utils/` 纯函数 |

### 3.4 建议优先覆盖的目标

| 优先级 | 目标 | 理由 |
| --- | --- | --- |
| 高 | `src/api/index.js` 拦截器 | 全站数据流出口，解包 / 错误码逻辑必须稳定 |
| 高 | `src/utils/auth.js` | Token 读写契约 |
| 高 | `views/meeting/hooks/useLiveKitRoom.js` 的事件→状态映射 | 房间事件是在线名单的唯一真相源，回归代价高（可抽成纯函数后测） |
| 中 | `views/homework/utils/{format,zip}.js` | 纯函数，测试成本低（`export.js` 已删除） |
| 中 | `views/ppt/utils/element.js`、`configs/*` | 纯逻辑（ID、颜色、几何计算） |
| 低 | 复杂渲染组件（PPT 元素渲染、Live2D 舞台） | 依赖画布与样式，性价比偏低 |
