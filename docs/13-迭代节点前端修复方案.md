> 项目：TrueBuddy
> 生效日期：2026-10-01 ｜ 规范入口：[README.md](./README.md)
> 适用范围：`frontend/src/views/workflow2/` 画布页的迭代节点（`type = 4`）前端缺陷修复
> 相关：[12-工作流规范.md](./12-工作流规范.md)、[11-测试规范.md](./11-测试规范.md)、[09-样式规范.md](./09-样式规范.md)

## 1. 背景与目标

迭代节点（`type = 4`）在画布上由「容器卡片 + 画布区 + 子块」三层结构组成，其布局口径、画布数据折叠与运行态归约分布在多个模块中。经逐文件排查，确认存在 **11 项前端逻辑缺陷**，覆盖数据正确性、视觉正确性与健壮性三类。

本方案的目标：

1. 按「数据正确性 → 视觉正确性 → 健壮性/可维护性」三档修完全部 11 项；
2. 每处布局口径与归约规则都可被 `frontend/tests/*.test.js`（Node 内置 `node:test`）锁定；
3. 不改变画布现有交互范式、不新增第三方依赖、不修改后端 `tb-module-workflow`。

约束（修复过程中必须遵守）：

- 不得破坏既有回归用例锁定的口径：尺寸下限装得下子块、节点拉宽后子块横向重新居中、悬空 `parentNode` 折叠后保留为顶层、嵌套迭代只展开一层且往返数据不丢、按事件携带的权威轮次计数；
- 不新增前端依赖，验证沿用 `frontend/tests/` 目录与 `cd frontend && npm test`；
- 后端行为只作口径参照，不产生后端改动。

## 4. 逐问题修复方案

### 4.1 P2 删除迭代容器后子块残留为游离节点

**问题现象与影响范围**

- 选中迭代容器卡片按 `Backspace`：容器消失，但子块全部保留，并以相对坐标（如 x≈76）错位渲染在画布左上区域；
- 再次点「运行」时，这些子块会被当作顶层节点提交，后端按「无入边接 `START`、无出边接 `END`」的规则**真实执行**；
- 残留子块的 `parentNode` 仍指向已删除的容器，被判定为「迭代体内节点」，因此运行结果面板永不渲染，用户完全看不到执行结果；
- 影响：画布数据完整性、提交给后端的定义正确性、编辑体验。级别 P0。

**根因分析**

- Vue Flow 删除键默认 `Backspace`，删除路径为 `removeNodes(getSelectedNodes.value)`；`removeNodes(nodes, removeConnectedEdges, removeChildren)` 的第三参数 `removeChildren` 默认 `false`（依据 `node_modules/@vue-flow/core/dist/vue-flow-core.mjs:6525` 的函数签名与 `:8237-8243` 的删除键处理），因此**不级联删除子节点**，而项目未接管删除流程（`WorkflowView.vue:241-249` 未设置 `deleteKeyCode`、无 `onNodesChange` 兜底）；
- `frontend/src/views/workflow2/utils/use-nested-node.js:18` 仅凭 `parentNode` 是否存在判定「在容器内」，容器消失后判定仍为 `true`，于是 `components/NodeResultPanel.vue:25`、`:37` 永久隐藏面板；
- `frontend/src/views/workflow2/utils/iteration.js:336-337` 的 `isTopLevel` 会把悬空 `parentNode` 的节点回退为顶层，这是加载容错的有意设计且已被 `frontend/tests/iteration.layout.test.js:70-80` 锁定，**本次不改**，改为在提交前清理残留节点。

**具体修复步骤**

1. `WorkflowView.vue` 关闭 Vue Flow 默认删除键并自管：给 `<VueFlow>` 传 `:delete-key-code="null"`（若实测 `null` 未生效则改传空数组），在画布容器上新增 `keydown` 监听处理 `Backspace` 与 `Delete`；
2. 键盘处理函数中先判断事件目标：命中 `input` / `textarea` / `select` / `[contenteditable]` 时直接返回，避免影响抽屉与节点内的确认输入框；
3. 删除动作统一走 `removeNodes(getSelectedNodes(), true, true)`，使容器与其直接子块、以及挂在它们上的连线一并删除；实现时以 `getSelectedNodes()` 作为**唯一**数据源，不自行维护选中集合；
4. `WorkflowView.vue` 新增 `cleanOrphanChildren()`：删除 `parentNode` 指向不存在节点的节点；在 `handleRun`（`WorkflowView.vue:153-164`）组装定义前调用一次，作为「任何路径产生的残留」的兜底；
5. 把「是否嵌套」抽成纯函数 `isNestedNode(nodes, nodeId)`（落在 `utils/iteration.js`），返回条件为「该节点的父容器在 `nodes` 中仍然存在」；`utils/use-nested-node.js` 改为调用它，`components/NodeResultPanel.vue` 的 `v-if` 表达式保持不变；
6. 抽屉版本收敛（同批处理 P9）：确认全局无引用后删除 `frontend/src/views/workflow2/NodeDataDrawer.vue`，并把其「删除节点」能力（原 `:450` 的 `removeNodes([current.id])`）并入 `components/NodeDataDrawer.vue` 的节点头部按钮，点击前用 `ElMessageBox.confirm` 二次确认，确认后同样调用级联删除。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/WorkflowView.vue` | 模板 `:241-249` 加 `:delete-key-code`；新增键盘删除、`cleanOrphanChildren`、提交前调用 |
| `frontend/src/views/workflow2/utils/use-nested-node.js` | `:16-19` 改为调用 `isNestedNode` |
| `frontend/src/views/workflow2/utils/iteration.js` | 新增导出 `isNestedNode` |
| `frontend/src/views/workflow2/components/NodeDataDrawer.vue` | 节点头部新增「删除节点」入口 |
| `frontend/src/views/workflow2/NodeDataDrawer.vue` | 删除（无引用） |

**验证方式**

- 自动化：新增 `isNestedNode` 用例 —— 父容器存在返回 `true`、父容器已被删除返回 `false`、顶层节点返回 `false`；
- 手工：选中容器按 `Backspace`，容器、子块、内部连线同时消失；删除后立即运行，提交体中不再出现游离子块；抽屉的删除按钮同样级联；删除无引用文件后 `cd frontend && npm run build` 通过。

**回滚方案**

- 回滚即移除键盘监听与 `:delete-key-code` 设置、恢复 `use-nested-node.js` 原判定、从 git 恢复被删文件。画布节点数据结构未变，无数据副作用。

### 4.2 P9 抽屉版本收敛

**问题现象与影响范围**

- `frontend/src/views/workflow2/` 下同时存在两份同名抽屉组件，实际生效的是 `components/NodeDataDrawer.vue`（由 `WorkflowView.vue:14` 引用），而根目录的 `NodeDataDrawer.vue`（1379 行，含删除节点、常量取值等能力）在全项目**无任何引用**；
- 后果：用户无法通过抽屉删除节点（工作台也没有其它删除入口）；后续维护极易改错文件。级别 P2。

**根因分析**

- 组件拆分过程中旧文件未下线；`WorkflowView.vue:14` 明确以相对路径引入 `./components/NodeDataDrawer.vue`；
- 根目录版本内含 `frontend/src/views/workflow2/NodeDataDrawer.vue:450` 的 `removeNodes([current.id])`，该能力未迁移到生效版本。

**具体修复步骤**

1. 全局检索 `workflow2/NodeDataDrawer`、`'./NodeDataDrawer.vue'`、`NodeDataDrawer` 三个关键字，确认根目录版本无引用（含路由、动态 `import`、`defineAsyncComponent`）；
2. 把「删除节点」能力迁移到 `components/NodeDataDrawer.vue` 的节点头部（见 P2 步骤 6），迁移时保留 `ElMessageBox.confirm` 二次确认；
3. 删除根目录旧文件；
4. 同步 [03-项目结构.md](./03-项目结构.md) 中该目录的文件清单（若其中列出了旧文件）。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/NodeDataDrawer.vue` | 删除 |
| `frontend/src/views/workflow2/components/NodeDataDrawer.vue` | 新增删除入口 |
| `docs/03-项目结构.md` | 目录清单同步（如有） |

**验证方式**

- 全局搜索确认旧路径无引用；
- `cd frontend && npm run build` 通过；
- 手工打开任意节点抽屉，点击「删除节点」后节点与其连线一并消失。

**回滚方案**

- 从 git 恢复被删文件即可；迁移过去的删除入口可独立移除，不影响其它功能。

### 4.3 P3 抽屉上游变量候选未按迭代体边界过滤

**问题现象与影响范围**

- 打开迭代容器**下游**节点（默认流程「结束」`900001`）的抽屉，候选里会出现迭代体内子块 `173594`（单份批改）的 `result`；选中后 `input.blockID` 被写成子块 id，而后端父图状态中不存在 `state[173594]`（子块状态只存在于迭代体子图内），运行期静默取到 `null`；
- 打开迭代体**内部**子块 `173594` 的抽屉，候选里会出现容器聚合输出 `132996.result` 与容器外 `100001` / `100002` 的变量；迭代体每轮只注入 `state[容器id] = { index, item, 当前项别名, variableParameters }`，这些引用运行期全部取不到值；
- 子块真正需要的 `item` / `index` / 迭代变量在任何节点的 `data.outputs` 中都不存在，抽屉里选不到，只能手写定义（`default-flow.js:119-122` 即为手写数据）；
- 影响：用户会配出「一定取不到值」的引用，属于静默错误。级别 P0。

**根因分析**

- `components/NodeDataDrawer.vue:141-169` 的 `getUpstreamNodes` 沿**所有**边反向遍历，不区分迭代体内部边；内部边以容器 id 作为虚拟出入口（`e-173594-132996` 的 target 是容器），因此从容器反向会命中子块、从子块反向会命中容器；
- `:178-188` 的 `getUpstreamOutputs` 直接把上游节点的 `data.outputs` 摊平，没有层级概念；
- `:198-200` 的 `watch` 源里只有 `getEdges.value.length`，边数量不变即不刷新。

**具体修复步骤**

1. 新建 `frontend/src/views/workflow2/utils/variable-sources.js`，导出纯函数 `upstreamOutputsOf(nodes, edges, nodeId)`。核心规则是「同层过滤」：
   - 令 `startParent` 为起点节点的 `parentNode`（顶层为 `null`）；
   - 反向遍历一条边时，仅当 `parentNode(edge.source)` 等于 `startParent`，或 `edge.source` 恰为 `startParent`（用于让迭代体子块拿到容器自身）时才接受该边；
   - 保留 `visited` 去重，防止容器自环导致死循环（沿用现有实现思路）。
   - 该规则一次性修好上述两类现象：顶层节点只会看到同为顶层的上游；迭代体内子块只会看到同一容器内的其它子块与容器本身；
2. 同模块新增 `injectOutputsOf(nodes, containerNode, nodeId)`：为迭代体内子块补充「迭代节点（每轮注入）」分组候选，包含 `index`（number）、`item`（object）、当前项别名（子块 `inputs` 中 `input.blockID` 等于容器 id 的 `input.name`，与后端 `IterateNode#collectItemVarNames` 同口径）、以及容器 `variableParameters` 的各项 `name`；候选项的 `blockID` 统一写容器 id；
3. `components/NodeDataDrawer.vue` 改为调用上述两个纯函数，删除本地 `getUpstreamNodes` / `getUpstreamOutputs`；`upstreamOptions`（`:235-253`）的分组逻辑保留，仅追加注入分组；`handleSourceChange`（`:269-299`）已有写回 `blockID` / `name` / `type` / `schema` 的能力，无需改动；
4. 刷新条件（同批处理 P10）改为监听 `computed` 指纹：由 `props.visible`、`props.nodeId`、每个节点的「`id` + 其 `data.outputs` 的 `name`/`type` 拼接串」、每条边的 `source`/`target` 拼接串组成，替换现有的 `getEdges.value.length`。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/utils/variable-sources.js` | 新建，承载 `upstreamOutputsOf` / `injectOutputsOf` |
| `frontend/src/views/workflow2/components/NodeDataDrawer.vue` | `:141-200` 改走纯函数；`:235-253` 追加注入分组 |

**验证方式**

- 自动化（`frontend/tests/variable-sources.test.js`）：
  - 默认流程中对 `900001` 调 `upstreamOutputsOf`，结果不含 `173594` 的任何变量；
  - 对 `173594` 调 `injectOutputsOf`，结果含 `item` / `index` / `jj`，且 `blockID` 均为 `132996`；
  - 对 `900001` 调 `upstreamOutputsOf`，结果仍包含容器 `132996` 的 `result`；
- 手工：抽屉保持打开时，改动上游节点输出变量名，候选列表立即刷新。

**回滚方案**

- 抽屉回退到本地遍历实现即可（新模块可保留但不引用，无副作用）；改动集中在 1 个新增文件与 1 个现有文件。

### 4.4 P10 上游候选列表刷新条件不足

**问题现象与影响范围**

- 抽屉打开期间，上游节点的 `outputs` 发生增删或改名，但连线数量不变时，候选列表不刷新，用户看到的是过期选项。级别 P2。

**根因分析**

- `components/NodeDataDrawer.vue:198-200` 的 `watch` 源为 `[() => props.visible, () => props.nodeId, () => getEdges.value.length]`，只监听边**数量**，既不监听节点数据也不监听边的两端。

**具体修复步骤**

1. 抽出 `sourcesFingerprint` 计算属性：拼接 `props.visible`、`props.nodeId`、`getNodes` 中每个节点的 `id` 与其 `data.outputs` 的 `name`/`type`、`getEdges` 中每条边的 `source`/`target`；
2. `watch` 改为监听 `sourcesFingerprint`，`immediate: true` 保留；
3. 一旦上游候选改由 `utils/variable-sources.js` 提供（见 P3），刷新逻辑与候选来源落在同一处，避免两套规则。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/components/NodeDataDrawer.vue` | `:190-200` 刷新条件 |

**验证方式**

- 手工：打开某节点抽屉，在另一处改名上游节点的输出变量（或增删变量行）后回到抽屉，候选列表已更新；
- 自动化：`sourcesFingerprint` 为纯计算，可由 `variable-sources.test.js` 间接覆盖（同名/改名的候选变化）。

**回滚方案**

- 单文件内改回按 `getEdges.value.length` 监听即可，无副作用。

### 4.5 P1 迭代卡片顶部内容区高度口径低估

**问题现象与影响范围**

- 口径把卡片头部记为「12 + 28 + 12 = 52px」，而实际 `.node-header` 内 `.node-title` 是 label 与副标题两行（合计约 35~44px，取决于行高），实际头部约 60~70px；变量行口径记 30px，而实际每行 32px（胶囊 `line-height: 22px` 加边框 2px，再加行距 8px）；
- 结果：约 3 个变量行时 `canvasTopOf` 比卡片内容底部小约 5~17px，画布区（不透明底色加边框的绝对定位块）**覆盖最后一行变量胶囊**；外侧 `in` / `out` 连接点的 y（`cardAnchorYOf`）同步偏上、不再与顶部内容区中线对齐；`canvasHeight` 高估使 `restackChildren` 的居中基准偏高；
- 影响：迭代节点一渲染即命中，全部迭代节点受影响。级别 P1。

**根因分析**

- `utils/iteration.js:69` 的 `headerHeight: 28` 只等于图标高度，未包含 `.node-title` 的两行内容；
- `utils/iteration.js:71` 的 `variableRowHeight: 30` 与 `components/VariableTags.vue:87-97`、`:113-124` 的实际行块（32px）不一致；
- 常量与 CSS 之间没有契约，也没有测试锁定，改动 CSS 会静默破坏布局计算；
- `node/IterateNode.vue:122-126` 的 `canvasHeight` 未扣减卡片边框（`--tb-border-width` 为 1px，见 `assets/theme.css:132`）。

**具体修复步骤**

1. 在 `node/IterateNode.vue` 的 CSS 中给标题行写入显式行高（`.node-label` 与 `.node-subtitle` 分别写 `line-height`），使「两行标题内容高度」成为可计算值；

### 4.6 P8 子块增删后容器尺寸不重算

**问题现象与影响范围**

- `layoutIteration` 在全项目无调用点，子块集合变化后容器尺寸停留在旧值：子块变多会溢出画布区，变少则在底部留下大片空白。级别 P2（当前画布无增删子块的 UI 入口，属边界与后续功能的地基）。

**根因分析**

- `utils/iteration.js:370-387` 定义了 `layoutIteration`（重算子块坐标与容器尺寸）但从未接线；
- `node/IterateNode.vue:137-163` 的 `restackChildren` 只更新子块 y，不更新容器高度。

**具体修复步骤**

1. 让 `layoutIteration` 成为尺寸重算的唯一入口，并把策略改为「只增不减」：高度取 `max(当前高度, minNodeSizeOf(rowCount, childCount).height)`，宽度同理（子块减少时保留用户自定义尺寸，与拖拽下限口径 `minNodeSizeOf` 保持一致）；
2. 在 `IterateNode.vue` 中以「子块 id 集合变化」为触发键调用 `layoutIteration`，替换当前 `restackChildren` 中只改 y 的那部分逻辑；子块 y 的重排行为保持不变（节点尺寸变化仍然不触发重排）；
3. 补一条防回归断言：子块增加时 `layoutIteration` 的结果不小于 `minNodeSizeOf`；子块减少时不缩小。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/utils/iteration.js` | `:370-387` 策略改为只增不减 |
| `frontend/src/views/workflow2/node/IterateNode.vue` | `:137-163` 接线调用 |
| `frontend/tests/iteration.layout.test.js` | 新增布局重算用例 |

**验证方式**

- 自动化：`cd frontend && npm test` 全量通过，含新增的 `layoutIteration` 用例；
- 手工：临时通过数据注入增加迭代体子块，确认容器随子块增高且子块不被裁切；减少子块后容器不缩小。

**回滚方案**

- `layoutIteration` 此前即无调用点，回退只需移除调用；改为「只增不减」的逻辑可随文件一并回滚，无回归风险。

### 4.9 P5 + P6 + P7 迭代进度归约与文案

**问题现象与影响范围**

- P5：嵌套迭代节点（迭代体里再放迭代节点）运行后，内层卡片进度永远停在 `0/N` 或不显示；
- P6：迭代源实际是标量时（后端 `NodeStateReader#toList` 会把标量按单项列表跑 1 轮），前端总轮数恒为 0，只显示「1 轮」且进度条恒为 0%；
- P7：旧后端事件不带 `state[容器id].index` 且迭代体有多个子块时，兜底累加会让完成轮数变成 N 倍，文案出现「4/2 轮」（进度条有 `Math.min(100)` 保护，文案没有）；
- 影响：进度展示错误，误导用户判断执行状态。级别 P1。

**根因分析**

- `utils/run-state.js:55-70` 的 `iterationPlanOf` 用画布 `parentNode` 推导 `children`；画布按 `utils/iteration.js:12-13` 只展开一层，内层容器在画布上没有子节点，`children` 集合恒为空，子块事件永远命中不到；
- `utils/run-state.js:44-48`、`:100-103` 只在取值是数组时更新 `total`，与后端「标量按单项列表」的口径不一致；
- `utils/run-state.js:96-98` 的兜底分支 `done + 1` 没有上限；
- 文案侧 `node/IterateNode.vue:93` 直接拼接 `${done}/${total} 轮`，未做钳制。

**具体修复步骤**

1. 新增导出纯函数 `toListLength(value)`：数组取长度；`null` / `undefined` 取 0（后端此时返回空列表、不执行轮次）；其余标量取 1。`withIterationProgress` 用它对迭代源产出求 `total`；
2. `iterationPlanOf` 跳过「画布上没有子块的迭代节点」（即 `children` 为空的内层容器），使 `iterationProgressOf` 返回 `null`，卡片不再渲染误导性的 `0/N` 进度行，徽标自然退回产出变量个数；保留 `node/IterateNode.vue:182` 的「嵌套 N」徽标作为该场景的唯一提示；
3. 兜底分支加钳制：`done` 取 `min(total（total 大于 0 时）或正无穷, done + 1)`；
4. `node/IterateNode.vue:89-94` 的 `progressText` 与 `:101-105` 的 `percent` 统一使用钳制后的值（`percent` 已有 `Math.min(100)`，文案需补齐）；
5. 在 [12-工作流规范.md](./12-工作流规范.md) 迭代章节补充已知限制：内层嵌套迭代体在画布上不展开，因此不展示内层轮次进度。

**涉及文件或模块**

| 文件 | 改动 |
| --- | --- |
| `frontend/src/views/workflow2/utils/run-state.js` | `:44-48`、`:55-70`、`:84-110` |
| `frontend/src/views/workflow2/node/IterateNode.vue` | `:89-94`、`:101-105` |
| `frontend/tests/run-state.iterations.test.js` | 新增用例 |
| `docs/12-工作流规范.md` | 补嵌套进度限制说明 |

**验证方式**

- 自动化：扩展 `frontend/tests/run-state.iterations.test.js` —— 标量源下 `total` 为 1；`total` 为 2 而收到 5 个子块事件时 `done` 恒不超过 2；`children` 为空的迭代容器其 `iterationProgressOf` 返回 `null`；既有两条用例（按权威轮次计数、无 `index` 时退回累加）必须保持通过；
- 手工：运行默认流程，观察进度行文案与进度条；构造标量源场景确认显示「1/1 轮」。

**回滚方案**

- `run-state.js` 为纯函数模块，单文件回滚；文案改动随 `IterateNode.vue` 单文件回滚，均无数据迁移。

## 8. 全局回滚方案

1. 按批次提交，每个批次一个独立提交，提交信息标注问题编号（如 `fix(workflow2): 迭代容器删除级联 P2 + 抽屉版本收敛 P9`），便于按批次 `git revert`；

3. 唯一需要单独确认的是文件删除（`workflow2/NodeDataDrawer.vue`）：删除前先做一次全局引用搜索并留档，回滚时从 git 恢复即可；

## 9. 风险与注意事项

1. 关闭默认删除键后必须自行实现删除，存在「新增键盘处理与 Vue Flow 内部选中态不同步」的风险：以 `getSelectedNodes()` 作为唯一数据源，不要自行维护选中集合；
2. `removeChildren` 的级联实现作用于**直接**子节点；当前画布只展开一层迭代体，若将来支持多层展开需重新评估；
3. `layoutIteration` 改为「只增不减」后，用户手动缩小的容器不会被自动改回，需在验收中确认与拖拽下限（`minNodeSizeOf`）行为一致；
4. 候选过滤规则收紧后，历史数据中已存在的「跨层引用」不会被自动改写，只会在下次编辑时不再出现在候选里；如需清理应按数据修复单独立项；
5. 布局口径改动会改变节点初始尺寸（`containerSizeOf` 的结果），重新加载定义后画布尺寸会变化，属预期修正，不作为回归；
6. 本方案不涉及后端；但 P3 / P11 对应的后端口径以 [12-工作流规范.md](./12-工作流规范.md) 为准，后端行为变化时须回头核对本方案的过滤规则。
