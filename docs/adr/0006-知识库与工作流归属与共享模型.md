# 知识库与工作流引入归属与共享模型（creator 过滤 + 公有/私有 + fork）

> 2026-11-16 ｜ 相关：[docs/doc-knowledgebase.md](../doc-knowledgebase.md)、[docs/doc-workflow.md](../doc-workflow.md)、[docs/doc-database.md](../doc-database.md)、[docs/specs/2026-11-16-首页tab与归属共享模型.md](../specs/2026-11-16-首页tab与归属共享模型.md)

## 背景

`kb_space` 与 `workflow` 现状是**全局池**：两表的列表接口（`getSpaceList` / `listWorkflows`）不按 `creator` 过滤，任何登录用户可见并可编辑所有空间与工作流；表上没有可见性字段。需求「知识库/工作流可设公有私有、用户可把别人的添加为自己的」要求先给这两个模块引入归属与权限概念——这是它们第一次拥有「谁拥有什么」的口径，改主意代价大（涉及存量数据迁移与权限语义），故立此存照。

## 决策

1. **归属唯一真相源 = 审计列 `creator`**（框架自动填充）：列表、编辑、删除均按它过滤与授权，不新建 owner/归属表。
2. **可见性 = 新增 `visibility SMALLINT`（0=私有/1=公有）**，新建默认私有，**存量一次性刷成私有**。
3. **共享语义 = fork 深拷贝**：「添加为自己的」生成完全独立的副本——工作流拷 `schema_json`（轻）；知识库复制空间+文档+版面块+分片+向量行并改写归属（重）。副本与原库此后**无任何同步**。
4. **公有的能力边界 = 可见 + 可 fork**：不可直接被检索增强选用，不可免 fork 直跑；检索增强只认「我的」资源，运行他人公有工作流必须先 fork。
5. **builtin 内置模板豁免**：「标准批改作业」（启动初始化器写入、固定 id）视为系统资产，全员可见可运行免 fork——否则批改链路的默认工作流会因 creator 过滤消失。
6. **编辑/删除仅创建者**；公有对他人只读。

## 为什么不是别的

- **引用订阅**（别人的公有资源以只读引用进我的列表，原作者更新实时可见）：实现最省、语义一致，但「添加为自己的」后用户无法改造副本，与「为自己的」的诉求相悖；用户明确选择了复制。
- **混合模式**（知识库引用 + 工作流复制）：各取最省机制，但同一个「添加」按钮在两个模块行为不同，认知负担；用户要求统一。
- **统一复制但知识库不复制向量**（副本使用时再解析向量化）：把成本转嫁到每次使用，大库 fork 后体验更差。
- **存量默认公有**：延续现状开放性，但权限模型形同虚设，多账号演示互相污染；用户选择更严的「全部私有」。

## 后果

- **存量刷私有后，多账号互相看不到旧资源**（升级即生效，已接受）。
- 知识库 fork 需复制 `vector_store` 行（`INSERT … SELECT` 改写 metadata 的 `spaceId/documentId/chunkId` 并生成新 uuid），大库 fork 有分钟级成本，接受（低频操作）。
- 「公有」必须有发现面：知识库页与画布页各新增「公有库」浏览区（落位见 spec 决策 14，属综合推导项）。
- `builtin` 豁免从此是长期特例：任何新的列表/运行入口都要记得带它。
