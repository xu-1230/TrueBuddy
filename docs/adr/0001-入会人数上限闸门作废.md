# 入会人数上限闸门作废

`join()` 曾用 `countOnline(meetingId) >= max-attendees(20)` 拒绝入会，而 `online` 是一个已退化、且**没有任何写入方能把它改回 false** 的字段（既无 leave 接口，前端也无 `beforeunload`/`pagehide`）。后果是老师关掉几个标签页之后，会议会在实际只有一人在线时抛「人数已满」，且无人能救——只能重开会。我们删掉这道闸门，连带作废 `tb.lecture.meeting.max-attendees` 配置与错误码 `1_007_000_005`。

## 备选方案

- **显式心跳 `POST /meeting/heartbeat` + join 前回收陈旧行**：能让闸门重新可信，但要新增两个接口、还要拍一个"多久无心跳算离线"的阈值。在单机、≤20 人、手机热点的演示场景里，这点收益不值这套机制。
- **闸门改问 LiveKit `RoomService/ListParticipants`**：最符合"成员真相在房间"，但会把 LiveKit 的 HTTP 可用性绑到入会热路径——LiveKit 挂了连门都进不去，而它本就是仓库外的独立进程。

## 后果

`max-attendees` 从此不再有语义；若日后要接公网或多租户，容量保护得重新设计（届时应基于房间事件计数，而非 DB 布尔列）。
