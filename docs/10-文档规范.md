## 1. 文档体系

项目文档采用「总入口 + 专题规范 + 决策/规格 + 子规约」结构：

```
docs/                              # 规范唯一来源（本目录）
├── README.md                      # 总入口与索引：项目简介、导航、阅读顺序、强制约定
├── 01-项目概述.md                  # 项目概述、项目定位、技术栈、整体架构
├── 02-编码规范.md                  # 前后端与 worker 编码要求
├── 03-项目结构.md                  # 后端多模块与包结构、前端目录结构、worker 结构
├── 04-组件规范.md                  # 前端组件写法、后端框架组件定位
├── 05-API规范.md                  # 统一返回、路径约定、接口清单、axios 层
├── 06-路由规范.md                  # 前端路由表与写法、后端 Mapping 约定
├── 07-状态管理.md                  # Pinia 组织、非 Pinia 状态与持久化、后端会话
```

### 1.1 职责边界

| 文档 | 定位 | 内容深度 |
| --- | --- | --- |
| `docs/README.md` + `01~12` | **规范源** | 要点化、可执行、可检查；不含冗长实现说明 |
| `docs/13~17` | **方案与落地记录** | 允许长文；必须显式区分「已落地 / 规划」，并写明生效日期与实测结论 |
| `docs/adr/NNNN-*.md` | **决策记录** | 一事一篇，只写背景、被否掉的选项、代价；**不回溯修改**，被推翻时新开一篇并互相链接 |
| `docs/specs/YYYY-MM-DD-*.md` | **变更规格** | 一次变更的范围、口径、验收项；落地完成后其结论要回写进对应专题文件或方案 |
| 根 `CONTEXT.md` | **领域术语表** | 只放术语定义与「不是什么」；实现细节链接到方案文档，决策链接到 `adr/` |
| `docs/ui.html` | **视觉样张** | 主题色阶、形态参数、组件外观的唯一基准：先改样张，再改 `theme.css`（见 [09](./09-样式规范.md) §3.3） |
| 两份子规约 | **细节来源** | 模块内部实现、完整配置、模块专属约定 |

> 同一事实只在最相关的文件中展开，其它文件以链接引用，避免多处维护导致失同步。

### 1.2 阅读与维护顺序

1. 新成员：`README` → `01` → `03` → `08`，再按角色补充。
2. 修改规范：先改 `docs/` 对应专题，再同步两份子规约中受影响的章节。

## 2. Markdown 书写约定

### 2.1 结构

| 项 | 要求 |
| --- | --- |
| 一级标题 | 每个文件**只有一个** `#` 标题，格式 `# NN - 主题` |
| 标题层级 | 最多到三级（`###`）；层级不得跳级 |
| 文件头 | 一级标题后紧跟引用块，写明「项目 / 生效日期 / 最近核对代码现状 / 规范入口 / 适用范围 / 相关」，字段与现有文件保持一致。**「最近核对代码现状」是这一篇的事实截止日期**：每次按实际代码复核过就把它改成当天，只改内容不复核不要动它 |
| 章节编号 | 二级标题带序号（`## 1. xxx`），便于交叉引用（如「见 §2.4」） |
| 分节顺序 | 同时涉及两端时：**先前端，后后端** |
| 结尾 | 可用一行引用块提示相关文件或注意事项 |

### 2.2 排版

| 项 | 要求 |
| --- | --- |
| 表格 | 优先用表格承载「多属性对照」「清单」类信息；表头必须完整（含对齐行） |
| 代码块 | 必须标注语言（`bash` / `js` / `java` / `json` / `yaml` / `text` / `mermaid`） |
| 术语 | 统一用中文 + 代码标识符，如「统一返回 `CommonResult<T>`」「上下文路径 `/api`」 |
| 标点 | 中文语境用全角标点；代码、路径、命令内部保持原样 |
| 空格 | 中英文之间加空格；文件名、类名、命令统一使用反引号包裹 |
| 目录树 | 用 ` ```text ` 代码块，注释用 `#` 对齐在行尾 |
| 强调 | 关键约束用**加粗**；提示、规划、注意用引用块 `>` |
| emoji | **不使用** |

### 2.3 链接

| 场景 | 写法 |
| --- | --- |
| `docs/` 内部互链 | 相对路径：`[05-API规范.md](./05-API规范.md)` |
| 指向子规约 | 空格需编码：`[前端子规约](../frontend/AGENT%20-%20前端技术规约.md)` |
| 指向源码 | 反引号路径（不建链接），如 `src/api/index.js` |

- 禁止出现指向已删除文件的链接（如旧的 `docs/AGENTS.md`、`../总体技术规约.md`）。
- 新增/重命名文件后，必须全量检索引用并同步。

### 2.4 内容红线

| # | 要求 |
| --- | --- |
| 1 | **现状与规划分离**：未落地的能力必须标注「规划 / 待开发」，并给出落地位置建议 |
| 2 | **不得美化**：代码与规范不一致时，按「现状 / 规范要求 / 待整改」三段式如实记录 |
| 3 | **禁止泄露敏感信息**：文档中不得出现任何真实密钥、口令、Token，只能写占位符名（如 `${OPENAI_API_KEY}`） |
| 4 | **不得留空章节**：章节标题下必须有实际内容，或标注「待补充」并说明责任人/触发条件 |
| 5 | **版本可核对**：技术版本号必须与 `pom.xml` / `package.json` 一致，改动依赖时同步更新 |
| 6 | **失同步是双向的**：已落地的能力不得继续挂在「规划 / 未实现 / 前端演示态」标签下，已删除的文件、端点、目录不得再作为现状描述；每次复核按「代码里是否存在」逐项打勾 |

## 3. 命名与存放

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 规范文件 | `NN-主题.md`，两位序号 | `05-API规范.md` |
| 总入口 | 固定 `README.md` | — |
| 子规约 | `AGENT - {端}技术规约.md`，置于对应子项目根目录 | `backend/AGENT - 后端技术规约.md` |
| 决策记录 | `adr/NNNN-决策标题.md`，四位序号递增，**不复用、不删除** | `adr/0002-在线状态唯一真相源为房间事件.md` |
| 变更规格 | `specs/YYYY-MM-DD-变更名.md`，以日期前缀排序 | `specs/2026-10-09-会议生命周期修复.md` |
| 领域术语 | 根目录固定 `CONTEXT.md`，只增改术语条目，不写实现细节 | — |
| 临时/过程文档 | **不提交到 `docs/`**；复现与草稿放 `.repro/`、`backend/tmp/` 等已被忽略的目录（`docs/notes/` 目前并不存在，别再往里写） | — |

## 4. 同步与评审

### 4.1 必须同步文档的代码变更

| 代码变更 | 需同步的文档 |
| --- | --- |
| 新增 / 删除 / 重命名接口 | [05-API规范.md](./05-API规范.md)（接口清单）、[06-路由规范.md](./06-路由规范.md)（映射前缀） |
| 新增路由 / 页面 | [06-路由规范.md](./06-路由规范.md) |
| 新增模块 / 目录调整 | [03-项目结构.md](./03-项目结构.md) |
| 依赖版本变更 | [01-项目概述.md](./01-项目概述.md)（技术栈表） |
| 环境变量增删 | [08-通用约束.md](./08-通用约束.md)（清单与 `.env.example`） |
| 放行白名单调整 | [05-API规范.md](./05-API规范.md) §2.4、[06-路由规范.md](./06-路由规范.md) §3 |
| 组件 / 样式约定变化 | [04-组件规范.md](./04-组件规范.md)、[09-样式规范.md](./09-样式规范.md) |
| **主题 Token 增删或取值变化** | 先改 [ui.html](./ui.html) 样张 → 再改 `assets/theme.css` → 最后同步 [09-样式规范.md](./09-样式规范.md) §3.3 的分层表 |
| 工作流接口、节点类型或定义字段变化 | [12-工作流规范.md](./12-工作流规范.md)、[05](./05-API规范.md) §2.5 |
| 会议 / 数字人链路变化 | [16](./16-PPT演讲与模拟会议方案.md)、[17](./17-AI数字人语音链路方案.md)；涉及术语口径变化时同步根 `CONTEXT.md` |
| **做出不可逆决策**（放弃某能力、改变唯一真相源、切断某条兼容路径） | 新增一篇 `docs/adr/NNNN-*.md`，并在受影响的专题文件里回链 |
| **开始一次多步变更** | 先落 `docs/specs/YYYY-MM-DD-*.md`，完成后把结论回写进专题文件，spec 保留不改 |
| 新增 / 调整测试 | [11-测试规范.md](./11-测试规范.md)（清单与命令） |
| 新增进程 / 部署形态（如 worker、外部服务） | [01](./01-项目概述.md) §4.3、[03](./03-项目结构.md)、[08](./08-通用约束.md) §5.2 |

### 4.2 评审要点

1. 事实是否与实际代码/配置一致（版本、路径、端口、接口）。
2. 是否区分现状与规划；待整改项是否可执行。
3. 链接是否可达；是否存在指向已删除文件的引用。
4. 是否泄露敏感信息。
