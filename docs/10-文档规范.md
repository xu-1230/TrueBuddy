## 1. 文档体系

项目文档采用「总入口 + 专题规范 + 子规约」两层结构：

```
docs/                              # 规范唯一来源（本目录）
├── README.md                      # 总入口与索引：项目简介、导航、阅读顺序、强制约定
├── 01-项目概述.md                  # 项目概述、项目定位、技术栈、整体架构
├── 02-编码规范.md                  # 前后端编码要求
├── 03-项目结构.md                  # 后端多模块与包结构、前端目录结构
├── 04-组件规范.md                  # 前端组件写法、后端框架组件定位
├── 05-API规范.md                   # 统一返回、路径约定、接口清单、axios 层
├── 06-路由规范.md                  # 前端路由表与写法、后端 Mapping 约定
├── 07-状态管理.md                  # Pinia 组织、后端无状态会话
├── 08-通用约束.md                  # 安全与配置、禁止事项、质量门禁
├── 09-样式规范.md                  # 作用域样式、主题、动效
├── 10-文档规范.md                  # 本文件：文档体系与书写约定
├── 11-测试规范.md                  # 测试现状与约定
└── 12-工作流规范.md                # 工作流接口参数定义与定义 JSON 规范

frontend/AGENT - 前端技术规约.md      # 前端子规约（细节来源，与 docs 为总—分关系）
backend/AGENT - 后端技术规约.md       # 后端子规约（细节来源）
```

### 1.1 职责边界

| 文档 | 定位 | 内容深度 |
| --- | --- | --- |
| `docs/README.md` + `01~12` | **规范源** | 要点化、可执行、可检查；不含冗长实现说明 |
| 两份子规约 | **细节来源** | 模块内部实现、完整配置、模块专属约定 |

> 同一事实只在最相关的文件中展开，其它文件以链接引用，避免多处维护导致失同步。

### 1.2 阅读与维护顺序

1. 新成员：`README` → `01` → `03` → `08`，再按角色补充。
2. 修改规范：先改 `docs/` 对应专题，再同步两份子规约中受影响的章节。

## 2. Markdown 书写约定

### 2.1 结构

| 项 | 要求 |
| --- | --- |
| 一级标题 | 每个文件**只有一个** `#` 标题，格式 `# NN - 主题` |
| 标题层级 | 最多到三级（`###`）；层级不得跳级 |
| 文件头 | 一级标题后紧跟引用块，写明「项目 / 生效日期 / 规范入口 / 适用范围 / 相关」，字段与现有文件保持一致 |
| 章节编号 | 二级标题带序号（`## 1. xxx`），便于交叉引用（如「见 §2.4」） |
| 分节顺序 | 同时涉及两端时：**先前端，后后端** |
| 结尾 | 可用一行引用块提示相关文件或注意事项 |

### 2.2 排版

| 项 | 要求 |
| --- | --- |
| 表格 | 优先用表格承载「多属性对照」「清单」类信息；表头必须完整（含对齐行） |
| 代码块 | 必须标注语言（`bash` / `js` / `java` / `json` / `yaml` / `text` / `mermaid`） |
| 术语 | 统一用中文 + 代码标识符，如「统一返回 `CommonResult<T>`」「上下文路径 `/api`」 |
| 标点 | 中文语境用全角标点；代码、路径、命令内部保持原样 |
| 空格 | 中英文之间加空格；文件名、类名、命令统一使用反引号包裹 |
| 目录树 | 用 ` ```text ` 代码块，注释用 `#` 对齐在行尾 |
| 强调 | 关键约束用**加粗**；提示、规划、注意用引用块 `>` |
| emoji | **不使用** |

### 2.3 链接

| 场景 | 写法 |
| --- | --- |
| `docs/` 内部互链 | 相对路径：`[05-API规范.md](./05-API规范.md)` |
| 指向子规约 | 空格需编码：`[前端子规约](../frontend/AGENT%20-%20前端技术规约.md)` |
| 指向源码 | 反引号路径（不建链接），如 `src/api/index.js` |

- 禁止出现指向已删除文件的链接（如旧的 `docs/AGENTS.md`、`../总体技术规约.md`）。
- 新增/重命名文件后，必须全量检索引用并同步。

### 2.4 内容红线

| # | 要求 |
| --- | --- |
| 1 | **现状与规划分离**：未落地的能力必须标注「规划 / 待开发」，并给出落地位置建议 |
| 2 | **不得美化**：代码与规范不一致时，按「现状 / 规范要求 / 待整改」三段式如实记录 |
| 3 | **禁止泄露敏感信息**：文档中不得出现任何真实密钥、口令、Token，只能写占位符名（如 `${OPENAI_API_KEY}`） |
| 4 | **不得留空章节**：章节标题下必须有实际内容，或标注「待补充」并说明责任人/触发条件 |
| 5 | **版本可核对**：技术版本号必须与 `pom.xml` / `package.json` 一致，改动依赖时同步更新 |

## 3. 命名与存放

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 规范文件 | `NN-主题.md`，两位序号 | `05-API规范.md` |
| 总入口 | 固定 `README.md` | — |
| 子规约 | `AGENT - {端}技术规约.md`，置于对应子项目根目录 | `backend/AGENT - 后端技术规约.md` |
| 临时/过程文档 | 不提交到 `docs/`；确需保留时放入 `docs/notes/` 并在 `README` 注明 | — |

## 4. 同步与评审

### 4.1 必须同步文档的代码变更

| 代码变更 | 需同步的文档 |
| --- | --- |
| 新增 / 删除 / 重命名接口 | [05-API规范.md](./05-API规范.md)（接口清单）、[06-路由规范.md](./06-路由规范.md)（映射前缀） |
| 新增路由 / 页面 | [06-路由规范.md](./06-路由规范.md) |
| 新增模块 / 目录调整 | [03-项目结构.md](./03-项目结构.md) |
| 依赖版本变更 | [01-项目概述.md](./01-项目概述.md)（技术栈表） |
| 环境变量增删 | [08-通用约束.md](./08-通用约束.md)（清单与 `.env.example`） |
| 放行白名单调整 | [05-API规范.md](./05-API规范.md) §2.4、[06-路由规范.md](./06-路由规范.md) §3 |
| 组件 / 样式约定变化 | [04-组件规范.md](./04-组件规范.md)、[09-样式规范.md](./09-样式规范.md) |
| 工作流接口、节点类型或定义字段变化 | [12-工作流规范.md](./12-工作流规范.md) |
| 引入测试框架 | [11-测试规范.md](./11-测试规范.md) |

### 4.2 评审要点

1. 事实是否与实际代码/配置一致（版本、路径、端口、接口）。
2. 是否区分现状与规划；待整改项是否可执行。
3. 链接是否可达；是否存在指向已删除文件的引用。
4. 是否泄露敏感信息。
